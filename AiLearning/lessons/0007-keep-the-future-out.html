Keep the future out of training

Your tangible win: detect data leakage before a suspiciously good validation score misleads a production decision.

What leakage is

Data leakage happens when training uses information that would not be available when the model makes its real prediction. It makes offline evaluation look better than the deployed model will be.

Ask one question for every feature: “Would I know this at the exact time I need to predict?” If not, it cannot be used as-is.

A simple example

You predict whether a patient will be readmitted when they leave hospital. A feature named number of follow-up visits in the next 30 days is highly predictive—but it occurs after discharge. It reveals the future, so it is leakage.

Time rule: calculate every feature using only information available before the prediction moment.

Leakage can hide in preprocessing

Suppose you standardize income by subtracting the dataset mean and dividing by its spread. If you calculate those values using all rows before the train/test split, the test set has influenced training. This is leakage even though the target label was never copied.

Safe order:

  1. Split the data into training and test sets.
  2. Fit the encoder, scaler, feature selector, or imputer on training data only.
  3. Transform training and test data with that fitted training-only process.

A pipeline packages those steps with the model, so the same safe order is applied during validation and production.

Two high-value warning signs

SignalQuestion to investigate
Unexpectedly excellent validation scoreDoes any feature contain a future outcome, a proxy for the label, or data from the test set?
Random split for time-dependent dataCould a later event appear in training while an earlier event appears in test?

For forecasting or any time-ordered process, evaluate on data that comes later than the training data. A random split can accidentally teach the model from the future.
